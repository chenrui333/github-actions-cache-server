# Direct downloads require verified tokens

A direct-download URL is a bearer credential: whoever holds it can read the merged object from storage until it expires, without asking the server again. The only thing standing between a caller and that URL is `getCacheScope`, which authorizes a lookup from the token's `repository_id` and `ac` claims. With `SKIP_TOKEN_VALIDATION=true` those claims are decoded but not verified, so any client that can reach the server can name any repository and scope and walk away with a signed URL for its cache. The server therefore refuses to start with `ENABLE_DIRECT_DOWNLOADS=true` and `SKIP_TOKEN_VALIDATION=true` together. `UNSAFE_ALLOW_DIRECT_DOWNLOADS_WITHOUT_TOKEN_VALIDATION=true` overrides the check for local testing only; it is named so that it cannot be set by accident. This extends ADR-0006: skipping verification stays a dev/test escape hatch, and the one feature that turns an unverified claim into a storage credential is now unreachable with it.

A signed URL lives `DIRECT_DOWNLOAD_URL_TTL_SECONDS` (default 600, the lifetime it had before the setting existed; at most 3600). Clients request the URL immediately before fetching it, and storage authenticates a GET when it starts rather than for its whole duration, so the lifetime only has to cover the start of the transfer and the client's retries, not a large restore. A shorter lifetime limits replay of a URL that leaks into job logs; with temporary AWS credentials, 300 or less also stays inside the window in which the AWS SDK refreshes them (5 minutes before they expire), so a URL is never signed by credentials that lapse before it does. Clients that cache a URL and fetch it later, such as BuildKit's `type=gha` cache importing a layer late in a build, need a longer lifetime. The Storage Reader Lease outlives the URL by a fixed margin (ADR-0002), so cleanup cannot delete an object while a transfer begun just before expiry is still reading it.

Token verification requires an `exp` claim, because jose only checks expiry when the claim is present. The optional `ACTIONS_TOKEN_AUDIENCE` pins the expected `aud`, restricting the server to tokens issued for one installation; a value that lists no audience (blank, or only commas) stops startup rather than silently disabling the check. Token rejections return and log the jose error code and failing claim name, never the token or its decoded claims, which jose attaches to its errors. Cache scope permissions are bit flags (read = 1, write = 2): lookups use only scopes with the read bit, and uploads only scopes with the write bit.
